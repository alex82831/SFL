# SFL 是否需要面向对象语法

**评估报告与决策建议** · 针对 SFL 0.5.0

本文回答一个问题：SFL 应不应该增加类、`this`、继承一类的面向对象语法。

所有数字都是在本仓库上实测的，命令随文给出，可复现。凡是估算，都标明是估算。

---

## 结论

| 提案 | 建议 | 一句话理由 |
| --- | --- | --- |
| 类 / 继承 / 原型委托 | **不做** | 语言已能表达封装、多态、组合；代价触及三层实现的 250 余处类型分派 |
| 用户对象上的 `this` | **不做** | 会把 `o.m()` 与 `o["m"]()` 割裂，而手册明确承诺二者等价 |
| **句柄类型上的方法语法** | **可做，若要花预算就花这里** | 唯一需求可测量、且**零兼容成本**的一处 |
| 模块命名空间 | **优先于以上全部** | 92 个手工前缀是实测痛点，收益覆盖整个标准库 |
| 先修本文发现的 4 个缺陷 | **立刻** | 与 OO 决策无关，但改变了权衡 |

一句话：**不要给用户对象加面向对象语法。真正缺的是命名空间，而它在标准库和内置函数命名里都留下了可测量的伤痕。**

## 一、现状：SFL 今天已经能表达什么

| 面向对象的能力 | SFL 今天 | 实测 |
| --- | --- | --- |
| 封装（私有状态） | 闭包 | ✓ |
| `o.m(x)` 调用语法 | 对象存函数值 | ✓ |
| 多态（同一消息，不同实现） | 不同构造器返回同名字段 | ✓ |
| 组合 / 委托 | 包装对象 | ✓ |
| 方法链的可读性 | `\|>` 管道 | ✓ |
| 共享方法表（省内存） | 外部对象 + 显式接收者 | ✓ |
| **开放递归**（覆盖后兄弟方法可见） | **闭包写法静默失效** | ✗ |

```sfl
def newCounter(start) {
  var n = start
  { "inc": (by) -> { n += by; n }, "get": () -> n }
}
val c = newCounter(10)
c.inc(5)                                    // => 15，方法调用语法今天就能解析
```

```sfl
def point(x, y) = {"x": x, "y": y}
def scale(p, k) = point(p.x * k, p.y * k)
def norm(p) = sqrt(p.x * p.x + p.y * p.y)
point(3, 4) |> scale(3) |> norm()           // 读起来就是 p.scale(3).norm()
```

**唯一真正的表达力缺口是开放递归**：一个方法调用同一对象上的另一个方法，且覆盖要生效。
闭包写法在这里会静默给出错误答案——闭包捕获的是定义时那个对象，不是接收者：

```sfl
val base = {"name": () -> "base"}
set(base, "describe", () -> "I am " + base.name())
val sub = copy(base)
set(sub, "name", () -> "SUB")
sub.describe()        // => "I am base"      覆盖被忽略，且不报错
```

而显式接收者写法今天就正确：

```sfl
val T = {"name": (self) -> "base", "describe": (self) -> "I am " + T.name(self)}
```

**所以整个诉求可以缩减为一句话：让调用点隐式传接收者。** 别的都已经有了。

> 复现：`docs/` 同级的任意脚本，`sfl x.sfl` 与 `sfl -c x.sfl -o x && ./x` 输出一致。

## 二、需求证据：这门语言实际是怎么被写的

全树 49 个 `.sfl` 文件、5393 行（不含 `legacy/`）：

```
函数值放进对象字面量的文件：1 个
x.y( 形式的方法调用：      1 处
```

两处都是同一行——`tests/compile/accept/higher_order.sfl:8`，而那是本次为了测试编译器
**新写的**用例。也就是说：**在作者自己写下的全部 SFL 代码里，面向对象写法出现 0 次。**

对照之下，记录 + 自由函数的写法遍布各处：297 处字段读取、267 个 lambda 作为参数传递。

### 唯一一个大到会痛的 SFL 程序

`stdlib/regex.sfl`（852 行）是仓库里唯一超出脚本规模的 SFL 程序。它手工搭出了四样
面向对象原语：

- **标签联合**：12 个构造点，11 种 `"kind"`；
- **动态分派**：`__reOne` / `__reNode` 里 10 处 `kind == "…"` 比较，位于匹配热路径上；
- **手写的 is-a 谓词**（`regex.sfl:393`）：
  `def __reOneCharKind(k) = k == "char" || k == "any" || k == "anynl" || k == "cls"`
  ——这就是 `nd instanceof SingleChar`，只是拼出来了；
- **一个缓存进实例的 vtable 槽**（`regex.sfl:409`）：`"one": __reOneCharKind(atom.kind)`，
  因为每次重算太慢。

这是仓库里最强的"应该有类"的信号。但同一个文件也给出了另一个信号：43 个函数
统一带 `__re` 前缀。**它真正缺的两样东西里，命名空间比类更迫切**（见第六节）。

> 复现：
> ```bash
> find . -name '*.sfl' -not -path './target/*' -not -path './legacy/*' \
>   -exec grep -nE '\b[a-z]\w*\.[a-z]\w*\(' {} +
> ```

## 三、代价：改动面是实测的，不是估的

新增一种"有身份、有类型名"的值，要同时改三层，而三层的语义必须**逐字节一致**
（这是编译器的既有契约，`tests/differential.sh` 在守）：

| 层 | 按类型分派的位置 |
| --- | --- |
| 解释器 `Value` 匹配点 | **103 处** |
| 运行时 C 的 tag 分派 | **150 处** |
| 编译器的 AST 遍历器 | **8 个**（`children` / `containsMakeFun` / `nodeRaises` / `callsAnything` / `tyOf` / `emitExpr` / `emitVoid` / `Dump.render`），全部带 `case _ =>` 兜底——漏掉一个分支能编译通过，运行时才出错 |

必须同步的语义面共 7 个：打印（`write`/`repr`）、相等、比较、`typeOf`、JSON 序列化、
迭代顺序、错误文本。

### 一个反直觉的发现：纯语法糖版的 `this` 其实很便宜

如果把 `this` 实现成**词法**的——占函数帧的 0 号槽，调用点把接收者塞进 `argv`——
那么三个本来最贵的问题全都免费：

- **嵌套闭包里的 `this`**：免费。`Parser.resolve` 已经会沿 `FnCtx` 链生成
  `OuterGet(depth, slot)`，闭包顺着现有帧链就捕获到了；
- **尾调用里的 `this`**：免费。`sfl_tail_set` 停放的就是 `argv`，接收者在里面，蹦床 0 行改动；
- **类型格**：0 行。`Ty` 完全不动，方法调用永远走已有的动态 `sfl_call` 路径。

保留字也不冲突：`this` / `class` / `new` / `self` / `extends` 在全部 SFL 代码里
作为标识符出现 **0 次**。

### 但它会割裂点号

`Parser.postfix` 里，`o.name` 与 `o["name"]` 生成**完全相同的 AST**（`Index` 节点），
再由同一个 `Call` 包起来。任何 `this` 设计都必须新增一个接收者感知的节点，也就必须
让两种写法分道扬镳——而《使用手册》第 689 行白纸黑字写着：

```sfl
println(o["name"])       // 张三
println(o.name)          // 同上，点号写法
```

更具体的后果：现有的 `table.inc(10)`（`tests/compile/accept/higher_order.sfl:8`）
在隐式接收者下会变成两个实参传给一参函数，直接报参数个数错误。**这个特性会改变现有
程序的含义，而不只是增加新写法。**

## 四、性能：修正我先前给出的数字

我先前说"闭包即对象在编译后慢 2×"。重测后这个说法不准确，需要更正。

**构建 200 万个实例（编译后，`timeNanos` 在进程内计时）：**

| 写法 | 耗时 | 相对 |
| --- | --- | --- |
| 外部方法表 `T.sum(o)` | 273 ms | **0.86** |
| 记录 + 自由函数 | 317 ms | 1.00 |
| 方法在实例里 `o.sum(o)` | 355 ms | 1.12 |
| 闭包，1 个方法 | 358 ms | 1.13 |
| 闭包，6 个方法 | 578 ms | **1.82** |

**调用同一个实例 300 万次（编译后）：**

| 写法 | 耗时 |
| --- | --- |
| 自由函数 `m(p)` | 152 ms |
| 外部表 `T.sum(p)` | 160 ms |
| `p \|> m()` | 179 ms |
| 闭包 `o.sum()` | 181 ms |

两点更正：

1. **代价随方法个数增长**，不是固定的 2×：单方法 1.13×，六方法 1.82×。代价在**构建**，
   因为每个实例要多分配 N 个闭包和一个堆帧。
2. **调用侧的差异很小，且不同的测法会给出不同的排序**（另一组用不同基准写法的测量把
   闭包排在最快）。因此调用性能不构成任何一方的论据。

**结论：性能不是加类的理由。** 最快的写法——外部方法表加显式接收者——今天就能写，
一个字都不用改语言。

顺带更正我先前的另一句话：`|>` 只在**可读性**上等价于方法链。`Parser` 在解析期就把
`x |> f()` 降解成静态调用 `f(x)`，它不做接收者分派。

> 复现：本文附带的两个基准脚本，`sfl -c perf.sfl -o perf && ./perf`。

## 五、顺手发现的四个缺陷

这些与 OO 决策独立，但它们改变了权衡（见下）。

**1. `jsonStringify` 对含函数的对象输出非法 JSON。** 它自己的 `jsonParse` 解析不了：

```sfl
val text = jsonStringify({"x": 1, "get": () -> 2})
// {"x": 1, "get": <fn lambda/0>}
jsonParse(text)     // Runtime error: invalid JSON at offset 16: unexpected character '<'
```

解释器与编译产物行为一致（差分测试看不到它）。Python 的 `json.dumps` 在这里抛
`TypeError`；建议照做，但这是语义变更，留给决策。

**2. `deepCopy` 无法深拷贝闭包捕获的状态。** 副本的方法改的是原件：

```sfl
def makeCounter(n0) { val self = {"n": n0}; self.inc = () -> { self.n += 1; self.n }; self }
val c = makeCounter(0)
val d = deepCopy(c)
d.inc(); d.inc()
// d.n = 0    c.n = 2        期望 d.n = 2, c.n = 0
```

这不是 `deepCopy` 的实现错误——任何动态语言都改写不了闭包已捕获的环境（Python 的
`copy.deepcopy` 同样如此）。**但手册没有说这一点。**

**3. 手册 §7.4 的建议在这个写法上会静默丢数据。** 手册说"要把数据交给线程又不担心被改，
传 `deepCopy(v)`"。照做：

```
4 个线程，各自 deepCopy(shared) 后自增 20000 次
每线程结果: [31994, 32921, 32508, 32418]      期望 [20000, 20000, 20000, 20000]
shared.n = 32921                              期望 0
```

无报错，解释与编译一致。这是手册给出的建议与语言的一处真实冲突。

**4. 手册第 303 行说"SFL 有 8 种运行时类型"，实际 `typeOf` 至少返回 18 种。**
少算的十种是句柄类型（`thread` `channel` `mutex` `atomic` `latch` `semaphore`
`process` `connection` `server` `file`）。

### 为什么这改变权衡

**所有"不要加实例，因为会破坏值语义和 JSON 往返"的论证，其实已经被当前推荐的替代写法
破坏了。** 一个"字段是数据、方法在类上"的类，在这两点上严格优于闭包即对象。

反 OO 的论证因此要弱一档：它不能再靠"保护值语义"站住，只能靠"需求不存在"和"代价太大"
站住——而这两条证据仍然充分。

## 六、被忽略的最强正面论据：SFL 已经有一套对象系统，只是私有的

`Value.scala:157`：

```scala
final class VHandle(val kind: String, val payload: Any, val label: String) extends Value:
  def typeName: String = kind
```

`typeName` 是运行时字符串，所以 `typeOf` 是开放的。Scala 侧的 `VHandle("…")` 与 C 侧的
`sfl_handle_new("…")` 给出同样的十个 kind。每一个都有：构造器、不透明的私有状态、
自己的打印形式（`<channel cap=1>`）、一组方法。**按本文用过的任何定义，这就是对象系统。**
作者需要"带身份和类型名的数据"，在宿主语言里给自己造了一套，却没有开放给 SFL 程序。

### 缺少接收者命名空间正在损害公开 API

321 个内置函数里，**34 个以类型名开头，纯粹是为了避开命名冲突**：

| 操作 | 今天的拼法 |
| --- | --- |
| close | `closeChannel` `closeServer` `closeSocket` **`fileClose`** |
| write | `processWrite` `socketWrite` `fileWrite` |
| readLine | `processReadLine` `socketReadLine` `fileReadLine`（外加读标准输入的 `readLine`） |
| size | `channelSize` `fileSize`（外加通用的 `size`） |
| alive | `isAlive`（线程） `processAlive`（进程） |

注意 `fileClose` 与 `closeChannel` 的**词序是反的**——一个操作四种拼法，命名约定在第四个
上就破了。

更能说明问题的是这一串：`close` `write` `read` `name` `port` `peer` `kill` `wait`
`alive` ——一门有文件、套接字、进程和线程的语言里最自然的九个动词，**没有一个能作为
裸名字使用**，因为三到五种类型都想要它。

### 而这一处的兼容成本恰好是零

```sfl
val c = channel(1)
c.size      // Runtime error: cannot index into channel
c.size()    // Runtime error: cannot index into channel
```

**句柄上的点号今天就是错误。** 给它加方法语法，没有任何现存程序能观察到变化——
不像用户对象上的 `this`，那会改变 `table.inc(10)` 的含义。而且它完全不碰 `VObj`、
不碰 JSON、不碰相等、不碰编译器的类型格。

这是整份评估里唯一一处"需求可测量 + 兼容成本为零"的交集。

## 七、决策建议

按性价比排序：

### 1. 先修四个缺陷（小，明确，与 OO 无关）

`jsonStringify` 遇到函数值应当报错而不是输出非法 JSON；手册需要说明 `deepCopy` 不拷贝
闭包捕获的状态，并修正 §7.4 的线程建议与第 303 行的类型数量。前者是语义变更，需要拍板。

### 2. 模块命名空间（收益最大）

92 个手工 `__` 前缀是实测的痛点，`import` 今天把被导入文件的一切都摊进全局命名空间
（实测：模块的内部函数 `helper()` 在导入方直接可见）。这件事的收益覆盖整个标准库和
所有多文件程序，而且不触碰值模型。

### 3. 若要一个"面向对象味"的特性，只做句柄上的方法语法

需求可测量（34 个带类型名前缀的内置函数、9 个不可用的动词），兼容成本为零
（点号在句柄上本来就是错误），实现面窄（不碰 `VObj` / JSON / 相等 / 类型格）。
这会让 `f.close()`、`s.write(x)`、`t.alive()` 成立，而 `closeChannel` 一族可以保留为别名。

### 4. 不做：用户对象上的 `this`、类、继承、原型委托

- 需求：作者自己 5393 行 SFL 里出现 0 次；
- 代价：三层 250 余处分派点、7 个必须逐字节一致的语义面、8 个无穷尽检查的遍历器；
- 副作用：割裂 `o.m()` 与 `o["m"]()`，改变现有程序的含义；
- 而它唯一能买到的表达力——开放递归——用显式接收者今天就能写对。

### 什么条件下我会改主意

- 出现第二个 500 行以上的 SFL 程序，并且它也像 `regex.sfl` 那样手写 is-a 谓词和
  缓存的 vtable 槽——那说明这是规模问题而非个例；
- 或者模块命名空间做完之后，`regex.sfl` 那类代码依然明显别扭——那说明缺的确实是对象；
- 或者出现需要**用户自定义句柄类型**的场景（比如给 SFL 写扩展），那时第 3 条会自然
  长成一个真正的对象系统，而那是有理由的长法。
