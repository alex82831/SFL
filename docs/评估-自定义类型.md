# SFL 是否需要自定义类型

**评估报告与决策建议** · 针对 SFL 0.6.0

本文回答一个问题：SFL 应不应该在语言层面支持**用户自定义的变量类型**——具名记录、
标签联合、以及顺带的类型注解。类、`this`、继承已由
[《评估-面向对象支持》](评估-面向对象支持.md)否决，本文不重评；这里只评"类型"。

所有数字都是在本仓库上实测的，命令随文给出，可复现。凡是估算，都标明是估算。

---

## 结论

| 提案 | 建议 | 一句话理由 |
| --- | --- | --- |
| 名义运行时类型（新 tag / 对象上的隐藏品牌 / `typeOf` 返回自定义名） | **不做** | 元组级的三层成本；可变对象上名义性买不到完整性；破坏 JSON 往返 |
| 声明式标签记录（`struct Circle(r)`，纯解析期糖） | **现在不做，条件触发** | 设计成立且便宜（编译器 0 行），但真实需求今天只有一处语料 |
| 类型注解 `def f(a: int)` | **另案评估** | 是另一个特性；stdlib 55 处手写校验是它的证据，与"自定义类型"无关 |
| 手册收录"标签记录"惯用法 | **已做（2026-08-19）** | 零实现成本，把 regex.sfl 的成功姿势变成官方姿势，并把三个静默坑写在明处 |
| 提取器模式放开点号 `case geo.Circle(r)` | **已做（2026-08-19）** | 纯解析器改动；让模块化的类型仿真顺滑；独立于任何类型决策 |

一句话：**不加。语言现有的模式匹配 + 标签对象 + 模块命名空间已覆盖诉求的大半；
剩余缺口值一节手册，不值一个类型系统。**但本文给出了"如果哪天要加，加成什么形状"
的完整规格与触发条件，届时不必重做调查。

> **落地记录（2026-08-19）**：结论表的后两条已实现。
> ① 使用手册 §5.7 新增"惯用法：标签记录"一节（构造集中、`select (x.kind)` 字面量
> 分派、`default: error(…)` 兜底），分派基准入库为 `bench/dispatch.sfl`；改在
> `docs/manual-template.md`，`tools/build-manual.sh` 重新生成。
> ② 提取器模式接受点号链——`case geo.point(x, y):`、`case T.of(x):`、任意深度的
> `a.b.f(p)` 均可，模块别名照旧在解析期解析。纯 `Parser.scala` 改动（触发前瞻、
> 元素预扫描把"单个点号"与 `...` 区分开、被调方按表达式规则构建），解释器、编译器
> 与运行时零改动；`tests/patterns.sfl` +12、`tests/namespaces.sfl` +3，全套件通过，
> 差分测试逐字节一致。第二节的"裸标识符顶棚"与第三节的 6 号失败模式自此消除，
> 正文保留当时的实测原貌。

## 一、"自定义类型"到底指什么

这个词至少混着四个提案，代价与收益完全不同，必须拆开定价：

1. **名义记录**：`typeOf(p)` 返回 `"Point"`，打印带类型名，错误消息带类型名；
2. **标签联合**：`enum`/ADT——一组互斥构造器 + 穷尽匹配检查；
3. **类型注解**：`val x: int`、`def f(a: array)`——声明处的契约检查；
4. **类与方法**：已否决，见面向对象评估，下文不再讨论。

## 二、现状：0.6.0 已经覆盖了诉求的大半

### 类型系统的今天

- 9 种字面量类型 + 10 种句柄类型，`typeOf` 共 19 个名字。**类型名集合在实现里
  是开放的**：`VHandle.kind` 是运行时字符串（`Value.scala:174`），C 侧
  `sfl_type_name` 对句柄直接返回 `v->u.h.kind`（`sfl_value.c:426`）——语言私下
  已经有"自定义类型名"，只是没开放给脚本。
- `select` 模式匹配：对象模式 `case {"kind": "circle", "r": r}:` 就是准 ADT
  匹配；9 个封闭的类型提取器（`Parser.scala:1289`）；**用户提取器是开放的类型
  模式**——任何返回 `null`/数组 的函数都能当 `case` 用。
- 0.5.0 评估的头号建议——模块命名空间——已落地：`_` 前缀私有 + `import as`。
  regex.sfl 重写后 43 个 `__re` 前缀清零，改为 55 个 `_` 私有名。

### 手写标签联合的痛点，落地后还剩多少

0.5.0 评估时 regex.sfl 的"应该有类"信号有四样。0.6.0 重写后复查：

| 信号 | 0.5.0 | 0.6.0 现状 |
| --- | --- | --- |
| 手工前缀 | 43 个 `__re` | **0**（命名空间接管） |
| kind 分派 | 热路径 10 处 `kind == "…"` if 链 | **2 个字面量 `select`**（`regex.sfl:548,561`），且比 if 链快约 25% |
| 手写 is-a 谓词 | 1 个 | 1 个（`_oneCharKind`，`regex.sfl` ） |
| 缓存进实例的 vtable 槽 | 1 个 | 1 个（`"one":`，`regex.sfl:409`） |

四样伤痕里两样已被别的特性治好，剩两样是真正属于"类型"的残余。

### 零语言改动能走多远：40 行 stdlib 原型实测

一个"类型"= 构造器 + 谓词 + 提取器，全是普通函数：

```sfl
def deftype(name, fields) { … }          // 见附录脚本，40 行
val Circle = deftype("circle", ["r"])
Circle.make(2)                            // {"kind": "circle", "r": 2}
Circle.make()                             // 报错: circle wants 1 field(s), got 0  ← 构造校验有了
val isCircle = Circle.of
select (s) { case isCircle(r): … }        // 提取器模式可用
```

实测可行，唯一的顶棚是**提取器只收裸标识符**：

```
case Circle.of(r): …
// Syntax error: expected ':' after a 'case' pattern, found '.'
```

所以模块化写法（`geo.Circle`）必须先绑一个平名，这是今天真实的别扭处。
（该限制已随本报告的第 2 项建议移除，见开头的落地记录；此处保留当时的实测原貌。）

## 三、缺口：六个实测的失败模式

没有自定义类型时，错误长这样（脚本与输出见附录）：

| # | 场景 | 今天的行为 | 严重度 |
| --- | --- | --- | --- |
| 1 | `case "circel":`——kind 字符串打错 | **静默落到 default，给错答案** | 高 |
| 2 | 构造时漏字段 `{"kind": "rect", "w": 3}` | 构造成功，**在远处使用点才炸** | 中 |
| 3 | `select` 无分支命中 | 静默返回 `null`（无穷尽性检查） | 中 |
| 4 | 拿错记录读字段 | `object has no key 'x'`——**不知道这对象是谁** | 低 |
| 5 | 跨库同形对象 | 结构相等，`==` 为真，无法区分来源 | 低 |
| 6 | 模块化提取器 | `case geo.Circle(r)` 是语法错误（已修复：现为合法写法） | 低 |

对照组很能说明问题：**凡是走名字的错误，语言today就给出带建议的定位错误**——

```
Runtime error: undefined variable 'circle'
  help: did you mean 'circl'?
```

字符串标签享受不到这些，因为它们对解析器只是数据。**任何"把标签从字符串提升为
名字"的设计，1 号失败模式自动变成带 did-you-mean 的定位错误**——这是声明式方案
的核心收益，也是它唯一买得到而惯用法买不到的东西（连同 2 号的构造期字段数校验）。

## 四、需求证据：这门语言实际是怎么被写的

全树 72 个 `.sfl` 文件、7,344 行（不含 `legacy/`；0.5.0 评估时是 49 个、5,393 行）：

- **标签联合的真实使用仍然只有 1 处**：`stdlib/regex.sfl`（852 行，12 个构造点、
  11 种 kind）。`tests/patterns.sfl` 里的第二处是模式匹配的展示用例，不是需求。
- **新增的第二个真实程序没有用标签**：`buildtool/main.sfl`（347 行）用 1 个中心
  记录 + 自由函数 + `spec?.name ?? __fail(…)` 的鸭子校验，写得很舒服——它是
  "记录 + 自由函数"够用的新证据，不是反例。
- **stdlib 手写参数校验 ≈ 55 处**（28 处 `error("…must be…")` + 27 处
  `if (!isX(…))` 守卫）。注意：这是**类型注解**的需求证据（"参数是 int"），
  不是**自定义类型**的需求证据（"参数是 Point"）——语料里没有一处在校验
  自定义形状。

0.5.0 评估留下的三个"改主意条件"逐条核对：

| 条件 | 现状 |
| --- | --- |
| 出现第二个 500+ 行、手写 is-a 与 vtable 的程序 | **未出现**（buildtool 用裸记录且无痛） |
| 命名空间落地后 regex.sfl 仍明显别扭 | **显著改善**（见第二节表格） |
| 出现用户自定义句柄类型的场景（扩展机制） | **未出现**（插件路线是子进程，不是 FFI） |

## 五、成本：三层对齐是实测的

### 语言加特性只有两条路，价差两个数量级

编译器手册（§4"新增语言特性的编译方式"）记录了两条既有路径：

- **贱路径——解析期糖**：模式匹配、多维下标走的路。解析器把新语法展开成既有
  节点，"编译器看到的与解释器执行的是同一棵树"，一致性自动成立，编译器 0 行。
- **贵路径——新运行时值**：元组走的路。实测触点：C 运行时 **23 处、横跨 5 个
  文件**（含 GC 精确遍历与 JSON），Scala 解释器 **16 处**，编译器 **7 处**，
  外加 34 条差分断言和手册章节。7 个语义面（打印、相等、比较、`typeOf`、JSON、
  迭代顺序、错误文本）必须逐字节对齐。
- 审计面比触点更大：当前 C 运行时有 **117 个 `case SFL_` 分支 + 102 处
  `tag ==` 比较**，Scala 侧 **约 265 个 `case V…` 匹配**——新增一个 tag 意味着
  这约 480 处都要过目一遍，漏掉的分支编译期不报错。

### 性能红线：热路径必须保留字面量 select

同一个标签联合、200 万次分派、三种写法（脚本见附录）：

| 写法 | 编译后 | 解释 |
| --- | --- | --- |
| A. 字面量 `select (s.kind)`（regex.sfl 热路径写法） | **108 ms** | 289 ms |
| B. 对象模式 `case {"kind": "circle", "r": r}` | 131 ms（1.2×） | 682 ms（2.4×） |
| C. 提取器（deftype 风格） | 204 ms（1.9×） | 1070 ms（3.7×） |

结论：任何把分派**强制**引向提取器调用的设计都会让 regex 级代码倒退；声明式
方案若做，`case Circle(r)` 必须在解析期展开成 B 级的内联测试（解析器认识
struct 名，不发调用），而不是 C 级的函数调用。这可行，因为模式本来就在解析期展开。

### 隐藏品牌的三重死穴

给 `VObj` 加一个打印/JSON 不可见的类型槽（"品牌"）看似便宜，实测三条都过不去：

1. **可伪造**：对象是可变的，`set(c, "kind", "rect")` 今天就能重打标签——品牌
   同样拦不住（除非再加对象冻结，那是更大的特性）。名义**完整性**在这个值模型上
   根本买不到，品牌相对可见字段没有增益。
2. **破坏 JSON 往返**：`c == jsonParse(jsonStringify(c))` 今天为真、标签保留、
   往返后照常分派（实测）。结构化数据出进程只有 JSON 一条路（通道传引用只限
   进程内），隐藏品牌一过序列化就蒸发——类型悄悄丢失比没有类型更糟。
3. **触全部 7 个语义面**：相等要不要看品牌、打印要不要带名、`typeOf` 返回什么，
   每一条都是两套实现的逐字节对齐 + 差分测试。

## 六、旁证：同类语言的选择

| 语言 | 定位对照 | 它的选择 |
| --- | --- | --- |
| Lua | 最接近：小、嵌入、表即万物 | 无自定义类型三十年；表 + 约定；元表的 `__name` 只影响错误消息 |
| Elixir | struct 的设计参照 | **struct = map + 保留键 `__struct__` + 编译期字段检查**——"标签就是普通字段、检查在编译期"的成熟先例 |
| Clojure | 数据优先的极端 | map + `:type` 关键字是主流姿势；`defrecord` 后加，动机是宿主互操作与性能，不是表达力 |
| JavaScript | 反面参照 | ES6 class 是生态规模（与 SFL 差 4–5 个数量级）逼出来的糖 |

模式很一致：**这个定位的语言没有一个因为"脚本写不下去"而加类型；后加的都是为了
生态、互操作或性能——SFL 三者都没有这个压力。**而如果哪天要加，Elixir struct
证明了"可见标签 + 解析期检查"这个形状在生产语言里站得住。

## 七、决策建议

按性价比排序：

### 1. 立刻：手册收录"标签记录"惯用法（零实现成本）——已做

在《使用手册》模式匹配一节后加一小节，内容三样：

- **姿势**：构造函数集中构造 + 首键放 `"kind"` + 热路径 `select (x.kind)` 字面量
  分派 + 需要模块化时用提取器（附平名绑定的写法）；以 regex.sfl 为范例。
- **三个坑**：kind 字符串打错不报错、`select` 无命中返回 `null`、漏字段延迟爆炸
  ——各给一行"怎么防"（构造集中化 + `default: error(…)` 兜底分支）。
- **一句定位**：SFL 的类型是数据的形状，不是名字；要名字，放进数据里。

### 2. 可做（小）：提取器模式放开点号——已做

`case geo.Circle(r):` 曾是语法错误（自由语法位，零兼容成本）。放开后
`import as` 的模块化类型仿真不再需要平名绑定。纯解析器改动，与任何类型决策独立。

### 3. 不做：一切名义运行时形态

新 tag、隐藏品牌、`typeOf` 返回自定义名、对象冻结——第五节三条死穴 + 第四节
需求缺位，全部否决。这与 0.5.0 面向对象评估的结论同向且互相加强。

### 4. 条件触发再做：`struct` 声明糖（规格已备好）

如果触发条件成立（见下），做的应该是这个形状，而不是别的：

```sfl
struct Circle(r)
struct Rect(w, h)

val c = Circle(2)                 // {"kind": "Circle", "r": 2}，字段数在构造点校验
select (s) {
  case Circle(r): 3.14159 * r * r // 解析期展开为内联 kind 测试 + 字段绑定（B 级性能）
  case Rect(w, h): w * h
}
```

- 标签是**普通的可见字段**——JSON 往返、`==`、打印、`typeOf` 全部不动，运行时
  两侧 0 行；
- 构造器与模式都是**解析期解析的名字**——打错 = 定位错误 + did-you-mean，漏字段 =
  构造点报错；穷尽性不承诺（与 select 语义一致），将来可在 `sfl check` 里做
  lint 级提示；
- 关键字用 `struct` 或 `type`（语料零占用）；**`data` 不行**——`bench/stdlib.sfl:34`
  已用作变量名；
- 声明随 `import` 在解析期可见（模块名字本就在解析期解析）；REPL 里重定义等同
  重定义全局。

估算（标明是估算）：解析器 + 测试 + 手册约几天量级，编译器与运行时 0 行——
与元组那种数周级、三层横跨的改动不是一个量级。

### 5. 类型注解：另案评估，不与本题捆绑

55 处手写校验是它的真实证据，但它是"契约检查"特性：值模型不动、名字集合不动，
纠结点在错误消息的措辞与定位如何与手写 `error(…)` 对齐（两套实现的错误文本是
逐字节对齐的）。值得单独一份短评估，不应搭本题的车。

### 什么条件下我会改主意

- 出现**第二个** ≥500 行、手写标签联合（is-a 谓词、kind 分派）的真实程序；
- 或跨模块共享标签数据发生**真实的** kind 冲突或静默错配事故（第三节 1 号失败
  模式在真实代码里咬人）；
- 或语言获得外部用户，且反馈集中于此；
- 或要给 LSP 做字段补全/形状提示——届时声明式记录是前置条件，直接按第 4 条规格做。
