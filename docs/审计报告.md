# SFL 代码审计报告

审计对象：`legacy/v0.0.1/`（原 0.0.1-Alpha 版本，2022 年）
审计日期：2026-08-14

本报告列出审计中发现的问题、验证方式，以及处理方式（除特别注明外均在 0.2.0 中完成）。

**验证方式**说明：
- **实测** —— 用原实现编译出的二进制复现过。为此需要先移除两处会导致链接失败的代码
  （见 B1、B2），复现用的临时工程保留在审计过程中，未并入仓库。
- **代码审阅** —— 通过阅读源码确认，未单独构造复现用例。

## 一、无法构建（阻断级）

### B1. 项目根本产不出原生可执行文件 — 实测

`PreDefs.scala` 的 `_httpGetProxy_imp` 使用了 `java.net.http.HttpClient`，
而 Scala Native 的 javalib 没有 `java.net.http`。`sbt nativeLink` 直接失败：

```
[error] Found 2 unreachable symbols!
[error] Unknown type java.net.http.HttpRequest$Builder, referenced from:
[error]  private method com.fartech.sfl.PreDefs$._httpGetProxy_imp(...) at PreDefs.scala:162
```

也就是说 README 里写的 `sbt nativeLink` 从来没有成功过；`sbt run` 走 JVM 可以跑，
但这与"编译成原生可执行文件"的项目定位相悖。

**0.2.0 的处理**：网络能力统一改用 sttp（在 Scala Native 上由 libcurl 支撑）。
`httpGetProxy` 改为通过 `ALL_PROXY` 环境变量让 libcurl 走代理。同时把
`withLinkStubs` 由 `true` 改成 `false`，让"缺少实现"在链接期暴露，而不是留到运行期崩溃。

### B2. `java.util.UUID.randomUUID()` 需要 `java.security.SecureRandom` — 实测

去掉 B1 之后链接仍然失败：javalib 不含 `SecureRandom`，它由
`scala-native-crypto` 提供。原 `build.sbt` 恰好声明了这个依赖，所以问题被掩盖了；
一旦有人精简依赖，链接就会断。

**0.2.0 的处理**：保留并升级 `scala-native-crypto`（0.2.1 → 0.4.0），它同时也支撑了
新增的 `md5` / `sha1` / `sha256`。

### B3. 构建配置写死了单台机器的路径 — 代码审阅

```scala
.withLinkingOptions(Seq("-L/opt/homebrew/opt/openssl@3/lib",
                        "-L/opt/homebrew/Cellar/libidn2/2.3.8/lib",
                        "-isysroot", "/Applications/Xcode.app/.../MacOSX.sdk"))
```

`libidn2` 带着具体版本号 `2.3.8`，Homebrew 升级一次就失效；SDK 路径写死后换机器即断；
Linux 上完全不可用。

**0.2.0 的处理**：改为在构建时用 `brew --prefix` 与 `xcrun --show-sdk-path` 动态探测，
探测不到就静默跳过，因此在 Linux 与没装 Homebrew 的 Mac 上同样能构建。

### B4. 工具链选择不稳健 — 实测

Scala Native 默认取 `PATH` 上的第一个 clang。本机 `PATH` 上是一个 LLVM 17，
而 macOS SDK 头文件要求 clang 19 及以上，编译 `eh.cpp` 时报
`use of undeclared identifier '__builtin_ctzg'`。

**0.2.0 的处理**：macOS 上显式用 `xcrun --find clang` 定位随 Xcode 分发的 clang，
它必然与 SDK 版本匹配。

### B5. 以 debug 模式编译 — 代码审阅

`withMode(Mode.default)` 就是 debug，未做优化。

**0.2.0 的处理**：默认 `releaseFast`，并可由 `SFL_BUILD_MODE` / `SFL_GC` / `SFL_LTO`
三个环境变量调节。

### B6. 误引入的 JVM 内部类 — 代码审阅

- `Main.scala:2`：`import com.sun.tools.attach.VirtualMachine.list`
- `Expr.scala:5`：`import sun.jvm.hotspot.HelloWorld.e`

两个都是 IDE 自动补全误加的，与业务无关，指向 JDK 内部模块。

## 二、正确性问题

### C1. 以换行结尾的脚本一律解析失败 — 实测

```
$ printf 'print(1)\n' > a.sfl && oldsfl -source a.sfl
'(' expected but end of source found
```

去掉结尾换行就正常。`parseByLine` 逐条解析语句，最后一条之后若还剩空白，
就会再解析一次并失败。几乎所有编辑器保存文件时都会补一个结尾换行，
也就是说这个语言几乎无法用编辑器正常写脚本 —— 仓库里的 `test.sfl` 恰好没有结尾换行。

**0.2.0 的处理**：一次性词法分析成 token 数组，`EOF` 是显式 token，空白与结尾换行
在词法层被吃掉。测试 `tests/run.sh` 中固定覆盖了带/不带结尾换行两种文件。

### C2. 函数调用会覆盖同名的外层变量 — 实测

```sfl
val counter = "outer"
def f(counter) { counter }
print(f("arg"))   // arg
print(counter)    // 原实现输出 arg —— 外层变量被形参覆盖了
```

`Environment.addNewVariable` 先调用 `findActualVariable` 沿作用域链向外查找，
找到同名变量就写到那一层去。函数的形参绑定因此会污染调用方。

**0.2.0 的处理**：作用域在解析期就解析完毕，局部变量编译成栈帧的数组下标，
根本不存在"按名字向外找"的过程。

### C3. 嵌套块里的 `return` 不生效 — 实测

```sfl
def f(n) {
  if (n > 0) {
    return "early"
  }
  "fell through"
}
print(f(5))   // 原实现输出 fell through
```

`BodyExpr.compute` 只在自己这一层的语句列表里识别 `ReturnExpr`，
嵌套块中的 `return` 求值后返回值被丢弃，控制流继续往下走。

**0.2.0 的处理**：`return` / `break` / `continue` 通过解释器上的信号位实现，
语句序列每执行一步后检查一次，可以从任意嵌套深度跳出。

### C4. 局部变量从不回收 — 代码审阅

```scala
def cleanupVariable(): Unit =
  Environment.variables.filter(_._1._2 == currentScope).foreach(_ => Environment.variables.remove)
```

`Environment.variables.remove` 缺少参数，作为表达式它只是把方法 eta 展开成一个函数值，
随即被 `foreach` 丢弃。**这个函数什么都没删。** 每次函数调用的形参绑定都会永久留在
全局 `HashMap` 里，长时间运行的脚本内存持续增长。

`cleanTempFunctions` 有类似问题：它只从 `tempFunctions` 里删，没有从 `functions` 里删；
而且 `tempFunctions: Map[Scope, FunDefExpr]` 一个作用域只能记一个函数，多的会互相覆盖。

**0.2.0 的处理**：栈帧随调用结束自然失效，交由 GC 处理，没有手工清理逻辑。

### C5. 布尔值不能放进数组字面量 — 实测

```sfl
val a = [true, false]
// java.lang.IllegalArgumentException: Expr (Value - true) cannot compute to value
//   at com.fartech.sfl.JsonArrayExpr.compute
```

`JsonArrayExpr.compute` 的匹配只覆盖 `NumberLiteral`、`String`、`HashMap`、`ListBuffer`，
漏了布尔值，也漏了 `null` 与函数。

**0.2.0 的处理**：值类型是一个封闭的 ADT，容器可以装下任意值。

### C6. `&&` 与 `||` 不短路 — 实测

```sfl
if (false && boom() > 0) then print("t") else print("f")
// 原实现：boom() 照样被调用并抛错
```

`LogicExpr.compute` 用 `foldLeft` 先把两侧都求值，再做布尔运算。这既是语义错误
（守卫式写法 `if (x != null && x.field)` 无法使用），也是性能损失。

**0.2.0 的处理**：`And` / `Or` 是独立的节点类型，右侧按需求值。

### C7. 非布尔条件的 `while` 抛 MatchError — 代码审阅

`LoopExpr.compute` 的匹配只有 `ValueExpr(v: Boolean)`、`ValueExpr(v: Double)`、
`ValueExpr(v: Long)` 三支。但数值在这个实现里一律是 `NumberLiteral`，
后两支永远匹配不上，写 `while (n)` 会抛 `MatchError` 而不是报错。

### C8. `ValueExpr.compute` 的强制转型 — 代码审阅

```scala
case EqualExpr(_, _)     => forceComputeToPrimitiveValue(value.asInstanceOf[FunExpr].compute)
case JsonValueExpr(_, _) => forceComputeToPrimitiveValue(value.asInstanceOf[FunExpr].compute)
```

两个分支都把值转成 `FunExpr`，而匹配到的分明是别的类型，一旦走到就是
`ClassCastException`。

### C9. `while` 的条件只接受比较表达式 — 代码审阅

```scala
def whileCond: Parser[LoopExpr] = "while" ~ "(" ~> compare ~ ")" ~ block ...
```

条件位置只允许 `compare`，因此 `while (i < n && ok)` 无法解析。

**0.2.0 的处理**：条件是完整的表达式。

### C10. 字符串转义几乎不可用 — 代码审阅

```scala
ValueExpr(str.replace("\"", "").replace("\\n", "\n"))
```

粗暴地删掉字符串里所有的双引号（含转义过的），并且只认 `\n` 一种转义。
`"say \"hi\""` 会被破坏成 `say hi`，`\t`、`\\`、`\uXXXX` 都不支持。

**0.2.0 的处理**：词法分析器完整处理 `\n \t \r \b \f \0 \\ \" \' \e \uXXXX`，
并支持单引号字符串与三引号跨行字符串。

### C11. `1e10` 这样的字面量会抛异常 — 代码审阅

```scala
if !f.contains(".") then IntegerLiteral(f.toLong)
```

`1e10` 里没有小数点，于是走 `"1e10".toLong`，抛 `NumberFormatException`。

**0.2.0 的处理**：词法层按指数、进制前缀、下划线分隔符分别处理。

### C12. `val` 的不可变性从不检查 — 实测

```sfl
val x = 1
x = 2
print(x)   // 原实现输出 2
```

`VariableExpr` 带着 `immutable` 标志，但没有任何地方读它。

**0.2.0 的处理**：解析期就拒绝对 `val` 赋值，并给出带行列号的错误。

### C13. 分支表用 `Map` 存储 — 代码审阅

`CondExpr(conds: Map[Expr, Expr], …)` 与 `SelectExpr(caseConds: Map[Expr, Expr], …)`
用 Map 保存分支。Map 不保证遍历顺序，也会让键相同的分支互相覆盖，
使 if/elsif 链的求值顺序在语言层面变成未定义的。

> 构造的若干用例（含 6 个重叠条件的分支链）在原实现上恰好都给出了正确结果，
> 因此这里只标记为**语义未定义的隐患**，而不是已复现的缺陷。

**0.2.0 的处理**：分支存成有序数组，按书写顺序求值。

### C14. `Environment.isDefined` 的逻辑连接词用反了 — 代码审阅

```scala
def isDefined(name: String): Boolean =
  lookupVariable((name, currentScope)).isDefined && lookupFun((name, currentScope)).isDefined
```

一个名字要同时是变量**且**是函数才算"已定义"，语义上应是"或"。
这个函数用于解析期检测重复声明，因此重复声明检测实际上从未触发。

### C15. 内置函数的参数会错位 — 代码审阅

```scala
imp(args.filter(arg => arg.isDefined && arg.get != None))
```

`newFun` 在把参数交给实现之前先过滤掉"未定义"的参数。一旦中间某个参数为空，
后面的参数就整体前移，`charAt(str, n)` 可能把 `n` 当成 `str`。参数全为空时
实现里的 `args.head` 还会抛 `NoSuchElementException`。

### C16. `length()` 对数组和对象抛 MatchError — 代码审阅

`_length_imp` 只匹配 `NumberLiteral`（抛错）与 `String`，数组和对象都会落空。

**0.2.0 的处理**：`length` 对字符串、数组、对象都有定义。

### C17. `import` 没有循环检测与去重 — 代码审阅

`importExpr` 直接读文件并递归解析，两个文件互相 import 会无限递归；
同一模块被多次 import 会被重复执行。查找路径也只有当前目录与
`$SFL_HOME/libs`，不包含引入方所在的目录，因此库里的相对 import 无法工作。

**0.2.0 的处理**：记录在途模块，成环时明确报错；已加载的模块再次 import 视为空操作；
查找路径增加了"引入方所在目录"。

## 三、性能问题

### P1. 每次函数调用都生成一个 UUID — 代码审阅 + 基准实测

```scala
val tempScope = Scope(UUID.randomUUID().toString, Some(scope))
```

`FunExpr.compute` 每次调用都要走一次 `SecureRandom`。这是调用密集型代码
慢上千倍的主因。

### P2. 变量访问是全局哈希表查找 — 代码审阅

变量存在 `mutable.Map[(String, Scope), Any]` 里。每次读写都要构造 `(String, Scope)`
元组、计算哈希，命中不了还要沿父作用域链一层层回溯。

**0.2.0 的处理**：解析期做词法定址，局部变量编译成 `Array[Value]` 的下标，
全局变量编译成一个整数索引，运行期没有任何按名字的查找。

### P3. 值被层层包裹 — 代码审阅

所有值都是 `ValueExpr[Any]`，而且会嵌套（`ValueExpr(ValueExpr(...))`），
`forceComputeToPrimitiveValue` 与 `getValueIfValid` 需要循环拆包，
并对已擦除的泛型类型做 `isInstanceOf` 判断。

**0.2.0 的处理**：封闭的值 ADT，不嵌套，小整数与布尔值走缓存。

### P4. 解析器基于 `JavaTokenParsers` — 代码审阅

parser combinator 在每个位置反复尝试多个正则、大量回溯，且没有记忆化。

**0.2.0 的处理**：手写词法分析器 + 递归下降解析器，并对字面量算术做常量折叠。

### 基准对比

同一台机器（Apple Silicon）、同一份输入、同样的 `releaseFast` + immix GC 构建。
每个用例先空跑一次预热页缓存，再取 10 次运行的均值（原实现太慢，只跑 1 次）。计时包含进程启动，
而当前实现的启动本身约 5 ms，因此纯计算部分的差距比表中更大。

| 用例 | 0.2.0 | 0.0.1 | 提升 |
| --- | --- | --- | --- |
| `fib(20)` 递归 | 7.0 ms | 19612.5 ms | **约 2800×** |
| 10 万次循环累加 | 10.6 ms | 179.9 ms | **约 17×** |
| 3 万次浮点迭代 | 8.2 ms | 88.2 ms | **约 11×** |

复现：`./bench/run.sh <原实现二进制路径>`

## 四、健壮性与易用性

### U1. REPL 遇到 Ctrl-D 会疯狂刷屏 — 实测

标准输入结束时 `readLine()` 返回 `null`，解析器对 `null` 抛异常，
异常被捕获后循环继续，于是无限循环。实测 3 秒内输出了 **45528 行**。

**0.2.0 的处理**：EOF 被显式识别为退出信号。

### U2. REPL 没有任何行编辑能力 — 代码审阅

原实现是 `while(true) { print(prompt); readLine() }`，没有历史、没有补全、
没有光标移动、无法多行输入、退格由终端驱动处理。

**0.2.0 的处理**：基于 POSIX termios 的原生行编辑器，含历史（跨会话持久化）、
前缀历史搜索、Tab 补全、实时语法着色、括号未配平时自动续行，
并正确处理中文等宽字符的光标定位。

### U3. 错误信息没有位置 — 代码审阅

解析错误只有 combinator 的默认文案；运行时错误是裸的异常消息，
既没有行号也没有调用栈。

**0.2.0 的处理**：所有错误都带文件名、行列号、源码摘录与插入符，
运行时错误还附带 SFL 层的调用栈；未定义的名字会给出拼写建议。

### U4. 深递归导致进程崩溃 — 代码审阅

没有调用深度上限，递归过深会耗尽原生栈，直接段错误。

**0.2.0 的处理**：调用深度上限（默认 3000，可由 `SFL_MAX_DEPTH` 调整），
超限时报告一条正常的运行时错误。

### U5. 命令行接口简陋 — 代码审阅

没有 `--help` / `--version`；未知选项直接 `exit(-1)`；`-source` 解析失败时
打印的是 "Unknown option"，与真实原因无关；错误信息与脚本输出都写到标准输出，
无法分离重定向。

**0.2.0 的处理**：完整的 `--help` / `--version`，位置参数形式 `sfl script.sfl args…`，
`-e` 直接求值，`--ast`、`--time`、`--no-color`；错误一律写标准错误；
退出码有明确约定。

### U6. 内置函数的错误信息无法定位 — 代码审阅

绝大多数内置函数的错误都是同一句 `"invalid argument"`，不说明是哪个函数、
第几个参数、期望什么类型。

**0.2.0 的处理**：统一为
`函数名: argument N must be <类型>, got <实际类型>`。

### U7. 仓库杂物 — 代码审阅

`sbt-launch.jar` 是一个 9 字节的空壳文件；`lib/` 是空目录；
多处 `.DS_Store` 被提交；`.idea/` 下的 IDE 生成物也在版本控制中。

## 五、未修改的设计取舍

以下几点是有意保留的设计选择，不作为缺陷处理，但已在手册中写明：

- **整数除法**：`int / int` 仍然得到整数（`7 / 2 == 3`），与 C、Java、Go 一致。
- ~~**闭包按帧捕获**：循环体内直接创建的闭包共享同一个循环变量。~~
  已在 0.3.0 中改为**逐轮捕获**：循环体若创建了函数，每轮迭代会分配独立的作用域，
  与 JavaScript 的 `let` 一致。不创建函数的循环仍走原来的扁平布局，没有额外开销。
- **`+` 的重载**：任一侧是字符串即做拼接，沿用原语言的行为。
- **错误处理不引入新语法**：用 `try(body, handler)` 内置函数，而不是 `try`/`catch` 语句。
