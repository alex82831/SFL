# 内置函数改用标准库实现会不会更快

**评估报告与决策建议** · 针对 SFL 0.8.2

本文回答一个问题：目前 367 个内置函数里，274 个是 C 原语（`runtime/*.c`）、91 个是
SFL 标准库（`stdlib/*.sfl`，预编译进 `libsflstd.a`）、2 个只有解释器有。如果把 C 原语
**尽可能改写为 SFL 标准库实现**，性能——尤其是编译后的性能——会不会有较大程度的提升？

所有数字都是在本仓库上实测的，命令与脚本随文给出，可复现。凡是估算，都标明是估算。

---

## 结论

| 问题 | 答案 | 依据 |
| --- | --- | --- |
| 编译后会更快吗 | **不会，恰恰相反**：受影响的函数慢 **15–300 倍** | §二表 1、表 2 |
| 解释执行会更快吗 | 更不会：慢 **20–440 倍** | §二表 1、表 2 |
| 至少调用开销会省吗 | 不会。两层的调用约定**逐字节相同**：装箱实参数组、不透明调用、装箱返回值 | §一 |
| 有没有哪类函数不亏 | 有：被用户回调主导的组合子（`map`/`filter`/`sort`……）——它们**已经**是 SFL 实现 | §四 |
| 真想提升编译后性能，路在哪 | **相反方向**：让编译器看穿更多内置函数。同一循环里 `sqrt`（原语）372 ms，`pow(x, 0.5)`（内联）14 ms，**27 倍** | §五 |

一句话：**内置函数的调用约定对两层实现一模一样，"改为标准库实现"唯一改变的是函数体的
实现语言——把 -O2 的 C 换成装箱值上的 SFL。编译器救不回来：容器元素在类型格里永远是
装箱的，标准库又是预编译的通用入口，逐位运算、逐字符取值全都退化成一次次运行时调用。
语言自己已经用脚投过票：`stdlib/codec.sfl` 里四个函数的 SFL 版至今躺在原处，被后来的
C 原语遮蔽。**

## 一、前提：迁移改变的只有函数体

这个问题成立的前提，是"两层实现对调用方有别"。实测代码路径：没有。

编译器对一次内置函数调用只有三条路（`Compile.scala:1742`）：

1. **16 个数值内联**（`Intrinsics.scala`）——参数类型已知时直接生成机器指令；
2. **C 原语**——把实参逐个装箱进 `argv`，`call ptr @sfl_p_xxx(i64 argc, ptr argv)`，
   结果类型 `Dyn`（`Compile.scala:1761`）；
3. **标准库函数**——同样装箱进 `argv`，`call ptr @sfl_call_code(@sflstd_xxx, …)`，
   结果类型同样是 `Dyn`（`Compile.scala:1770`）。

路 2 与路 3 对调用点完全等价：一样的装箱、一样的不透明调用、一样把类型推断截断成
`Dyn`。标准库模块又是**独立预编译**成 `.o` 归档的（`Backend.scala:169`）——编译它们时
不知道任何调用点的类型，只有通用入口，用户程序也不与归档做 LTO。所以"把一个 C 原语
改为标准库实现"，调用开销一分不变，变的只有函数体：从 clang -O2 的 C，换成 SFL 编译器
为装箱值生成的代码。

层本身的确是免费的。把 `stdlib/coll.sfl` 的 `sum` 原样拷进用户程序编译（可特化的一侧），
与走 `libsflstd.a` 的 `sum` 计时相同：

| sum（20000 元素 × 100 次，编译后） | 毫秒 |
| --- | --- |
| 标准库 `sum`（经 `libsflstd.a`） | 154–179 |
| 同一函数体拷进用户程序 | 154–174 |

问题不在归档，在函数体。

## 二、实测：函数体换成 SFL 的代价

环境：Linux x86_64，发布版 `sfl 0.8.1` 二进制（校验和一致；0.8.2 相对 0.8.1 未改
`stdlib/`，运行时只有缺陷修复，分层架构不变），clang -O2（默认），每组多轮取稳定值。
脚本全文见附录。

### 表 1：天然对照组——同一个函数，仓库里就有两份实现

`base64Encode` / `hexEncode` 在 `runtime/sfl_codec.c` 有 C 原语，在 `stdlib/codec.sfl`
有 SFL 实现（今天被原语遮蔽）。把 SFL 版换个名字拉进基准，两版输出先断言相等再计时
（1.8 KB 文本 × 300 次）：

| 函数 | C 原语 | SFL 标准库实现 | 慢多少 |
| --- | --- | --- | --- |
| base64Encode，编译后 | 2 ms | 297–336 ms | **≈150 倍** |
| base64Encode，解释 | 5 ms | 327 ms | ≈65 倍 |
| hexEncode，编译后 | 3 ms | 356–384 ms | **≈120 倍** |
| hexEncode，解释 | 5 ms | 313 ms | ≈63 倍 |

这不是刻意写慢的稻草人——就是标准库自己的实现，还删去了代理对分支（删掉后只会更快）。

### 表 2：把字符串原语改写成 SFL 会怎样

三种写法各代表一类迁移：纯 SFL 重写（`indexOf` 逐字符扫描）、"组合既有原语"的胶水式
重写（`replace` 用 `strFind`+`substring` 拼接，扫描仍在 C）、逐字符重建（`reverse`）。
输出先断言与原语一致：

| 函数（编译后） | C 原语 | SFL 改写 | 慢多少 |
| --- | --- | --- | --- |
| indexOf（4.4 KB 干草堆 × 400） | 2 ms | 160–176 ms | **≈85 倍** |
| replace（3 KB × 400，胶水式） | 3 ms | 39–46 ms | **≈15 倍** |
| reverse（3 KB × 400） | 1 ms | 317–340 ms | **≈300 倍** |

解释执行同样的改写：indexOf 慢 440 倍、replace 慢 22 倍、reverse 慢 13 倍。

**两处值得盯住的反常**：hex 与 reverse 的 SFL 版**编译后（384 / 332 ms）比解释执行
（313 / 232 ms）还要慢**。编译器手册 §11 说装箱代码编译只快 2–3 倍，因为分配、哈希、
间接调用两边成本相同；在逐字符分配的循环里，这个比值实测收敛到 1 以下——编译产物的
每次 `charAt` 都是一次真堆分配加回收器压力，解释器的同一操作只是 Java 字符串取字符。
**"编译后"不是这类代码的救星，连下限都保不住。**

### 表 3：已经迁过去的 91 个，代价今天就看得见

官方基准 `bench/stdlib.sfl`（注释原话："the standard-library hot paths: what the
modernization must not slow down"）解释 vs 编译：

| 基准 | 解释（原生实现） | 编译（SFL 实现） | 编译后是快是慢 |
| --- | --- | --- | --- |
| regex match | 44 ms | 91–96 ms | **慢 2.1 倍** |
| regex findAll | 9 ms | 16 ms | 慢 1.8 倍 |
| regex replace | 16 ms | 25–27 ms | 慢 1.6 倍 |
| sort | <1 ms | 4 ms | 慢约 4 倍 |
| sortBy | 1 ms | 4–5 ms | 慢约 4 倍 |
| map+filter+reduce | 50 ms | 13 ms | **快 3.8 倍** |
| assocIn/getIn | 28 ms | 18–19 ms | 快 1.5 倍 |
| base64/hex 往返 | 2 ms | ≈0 ms | 快（编译走的是 **C 原语**） |

同一行里，解释一侧跑的是 Scala 原生实现（`sort` 是 `java.util.Arrays` 一族，regex 是
Java 引擎），编译一侧跑的是 `stdlib/*.sfl`。已经 SFL 化的"发动机件"（正则引擎、排序）
**编译后反而输给解释器**；`sum` 单测更直白——原生 12 ms 对 SFL 版 165 ms，**13 倍**。
这就是"改为标准库实现"的现价，今天已经在账上。把剩下 274 个 C 原语也这样迁过去，
等于把这一列扩到 I/O、JSON、哈希、全部字符串操作。

## 三、机理：为什么编译器救不了 SFL 函数体

四条，每条都能在代码里指到：

1. **容器元素永远装箱。** 类型格只有 `I64 / F64 / Bool / Dyn`（手册 §5）——没有
   "整数数组"这种类型。`bytes[i]` 取出的永远是堆上的装箱值，函数体再怎么被推断，
   逐元素的循环也拆不了箱。这是值模型的设计决定（任意值可进任意容器），不是推断不够强。
2. **标准库是预编译的通用入口。** 每模块一次、脱离调用点编译（`Backend.scala:169`），
   参数以 `(env, argc, argv)` 进来，没有特化，也没有跨归档内联（无 LTO）。
3. **"指令级"操作在 SFL 里是一次调用，在 C 里是一条指令。** 16 个内联之外的一切——
   `bitAnd`、`shiftLeft`、`charAt`、`ord`、`push`——都走装箱调用约定。
   `stdlib/codec.sfl` 的 base64 主循环每 3 个字节要过约 20 次这样的调用（还不算
   UTF-8 预编码那一趟每字节的 `charAt`+`ord`+`push`）；`sfl_codec.c` 的同一循环是
   几条移位加一次表查。150 倍就摊在这里。
4. **分配与回收。** SFL 版 `reverse` 每字符分配一个单字符字符串单元，`join` 再按
   O(n log n) 拷贝合并；C 版一次分配定长缓冲顺序写。分配密集正是表 2 反常（编译后
   慢于解释）的原因。

## 四、现有分层已经站在正确的一侧

手册 §7 的分层原则经得起上面的数字检验：

- **真原语归 C**：I/O、系统调用、字符串码元操作、分配、时间、哈希、JSON——正是
  改写代价 15–300 倍的那一类。
- **可组合的归 SFL**：`map`/`filter`/`reduce`/`groupBy`、`assoc`/`getIn`、函数组合子——
  成本被**用户回调与分配**主导，实现语言无关紧要，而编译器处理闭包调用比解释器好，
  所以这一类编译后反而快 3.8 倍（表 3）。它们是唯一"SFL 化不亏"的形状，而它们已经
  全部在 SFL 一侧了。
- **正则引擎**是刻意的例外：用 2 倍于 Java 引擎的速度，买断了外部依赖并让两个引擎
  行为逐字节一致（手册 §8 列明差异）。那是一致性采购，不是性能采购。
- 仓库里还留着一次**反向迁移**的化石：`stdlib/codec.sfl` 的 `base64Encode`、
  `base64Decode`、`hexEncode`、`hexDecode` 四个公开定义被 `primitives.def` 里的同名
  C 原语遮蔽（编译器按原语优先解析，`Compile.scala:1746`；解释器走 Scala 原生），
  只剩 `urlEncode`/`urlDecode` 还在用它们的私有助手。方向是从 SFL 走向 C，不是反过来。

结论性判断：**当前 274 / 91 的边界画对了。可迁而不亏的早已迁完；剩下的每一个迁移都是
纯损失。**

## 五、真想提升编译后性能，杠杆在反方向

问题的直觉——"编译后 SFL 和 C 都是机器码，应该差不多"——错在忽略了装箱边界。真正
消除这条边界的手段是**让编译器看穿内置函数**，而不是换实现语言。同一份循环体的实测：

| 写法 | 编译路径 | 40 × 20 万次迭代 |
| --- | --- | --- |
| `acc += sqrt(x)` | C 原语：装箱 → 调用 → 拆箱 | 372 ms |
| `acc += pow(x, 0.5)` | 内联表命中：一条 `llvm.pow` | **14 ms（27 倍）** |

同是"内置函数"，差别只在编译器认不认识它。若要花预算，按杠杆排序：

| 措施 | 预期 | 性质 |
| --- | --- | --- |
| 扩大内联表：位运算 6 个、`sqrt`/`cbrt`/`log`/`tan` 带域检查、已知 `(string, int)` 上的 `charAt`/`ord` | 数值与扫描热点一到两个数量级（参照 sqrt 27 倍；域检查是两条比较） | 估算，机制已验证 |
| 标准库随程序编译（丢归档，参与特化与内联） | 组合子的调用/分派开销消失；但容器元素仍装箱，上限就是手册 §11 的 2–3 倍带；每次编译多付约百毫秒 | 估算 |
| 用户程序链接开 thin-LTO，跨归档内联原语 | 小头；原语体大，内联收益集中在 `length` 一类小函数 | 估算 |
| 维持现边界，改动前后跑 `bench/stdlib.sfl` | 守住已有的 91 个不再变慢 | 现行做法 |

def bench(name, reps, f) {
  val t0 = timeNanos()
  var i = 0
  var last = null
  while (i < reps) {
    last = f()
    i += 1
  }
  println(padEnd(name, 26) + padStart(toString((timeNanos() - t0) / 1000000), 6) + " ms  " + last)
}

**bench2_string.sfl** —— 三个改写，输出先断言与原语一致：

```sfl
def sIndexOf(s, needle) {          // 纯 SFL：逐字符扫描
  val n = length(s)
  val m = length(needle)
  if (m == 0) { return 0 }
  val limit = n - m
  var i = 0
  while (i <= limit) {
    var j = 0
    var ok = true
    while (ok && j < m) {
      if (charAt(s, i + j) != charAt(needle, j)) { ok = false }
      j += 1
    }
    if (ok) { return i }
    i += 1
  }
  -1
}

def sReplace(s, from, to) {        // 胶水式：扫描仍在 C 原语 strFind 里
  var buf = ""
  var i = 0
  while (true) {
    val at = strFind(s, from, i)
    if (at < 0) {
      if (i == 0) { return s }
      return buf + substring(s, i, length(s))
    }
    buf = buf + substring(s, i, at) + to
    i = at + length(from)
  }
}

def sReverse(s) {                  // 逐字符重建
  val out = []
  var i = length(s) - 1
  while (i >= 0) {
    push(out, charAt(s, i))
    i -= 1
  }
  join(out)
}

val hay = repeat("lorem ipsum dolor sit amet consectetur adipiscing elit ", 80) + "NEEDLE tail"
val doc = repeat("one two three four five six seven eight nine ten ", 60)
```
